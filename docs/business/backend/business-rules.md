# Business Rules Catalog
# Business Rules: Auth, Users, Notifications

- **BR-AUTH-01**: Usernames and Emails must be unique across the system.
- **BR-AUTH-02**: A Guest user cannot log in via `guestToken` if their role has been changed (upgraded to USER).
- **BR-AUTH-03**: Guest usernames follow the pattern `guest_{random8}`.
- **BR-AUTH-04**: Access tokens are short-lived stateless JWTs; Refresh tokens are stateful and stored in Redis with `{jti}`.
- **BR-USER-01**: Users are softly deleted by setting `deleted_at`.
- **BR-USER-02**: Avatar uploads use Cloudinary and append `UUID` to usernames to avoid collisions. Old avatars are deleted asynchronously.
- **BR-PRES-01**: Presence is tracked per-session. A user is `ONLINE` if they have at least one active session.
- **BR-PRES-02**: If a user disconnects while `IN_ROOM` (playing), they are given a grace period to reconnect before fully dropping from the game.
- **BR-NOTIF-01**: Notifications can be marked as read but not unread.
# Chess Business Rules

- **R01**: A user can only create a room if they are online.
- **R02**: A user can only join a room if they are online.
- **R03**: A game is not persisted to the database until it finishes. Active games reside in Redis.
- **R04**: If a room is private, unauthorized players cannot join (handled at join phase).
- **R05**: A player cannot switch to a seat (White/Black) that is already taken.
- **R06**: Spectators cannot join if the room setting `spectatorLocked` is true.
- **R07**: When the host leaves the room, the host role is transferred to a random remaining user. If the room is empty, it is deleted.
- **R08**: If a player leaves during the `COUNTDOWN` state, the countdown is immediately cancelled, and the room returns to the `WAITING` state.
- **R09**: Chat is disabled if the room's `isChatLocked` setting is true.
- **R10**: A player can only make a move if it is their turn.
- **R11**: Time deducted on a move equals the time elapsed since `turnStartedAt`. If this brings time below zero, the player loses by timeout.
- **R12**: When a move is made, the player receives an increment in seconds added to their remaining time.
- **R13**: Draw offers are valid for 30 seconds (TTL).
- **R14**: A player cannot accept their own draw offer.
- **R15**: The PGN format is generated by chesslib. If generation fails, it falls back to simple UCI move notation.
- **R16**: The game can end due to Checkmate, Stalemate, Resignation, Timeout, Draw Agreement, or Draw (by threefold repetition/50-move rule handled by chesslib).
- **R17**: Chat history retains a maximum of 10 messages per room.
- **R18**: The turn timer runs as a ScheduledFuture in the backend and triggers `endGameByTimeout` when it fires.
# Forums Business Rules

- **FRM-RULE-001**: A post must be submitted with content formatted as valid Tiptap JSON schema.
- **FRM-RULE-002**: Images uploaded for a post are initially `ORPHAN`. They become `ATTACHED` only when explicitly parsed and extracted from the post's Tiptap JSON payload upon creation.
- **FRM-RULE-003**: `ORPHAN` images older than 1 hour are automatically permanently deleted from storage and the database.
- **FRM-RULE-004**: All newly created posts start in `PENDING` state and must undergo automated AI moderation.
- **FRM-RULE-005**: Only `APPROVED` posts are visible to the general public, can be liked, and can be commented on.
- **FRM-RULE-006**: Users can only view their own `PENDING` or `DENIED` posts.
- **FRM-RULE-007**: Users can only delete their own posts.
- **FRM-RULE-008**: Comments support a maximum nesting depth of 2 (Root Comment -> Reply). A reply cannot have another reply.
- **FRM-RULE-009**: A reply must belong to the same post as its parent comment.
- **FRM-RULE-010**: Liking a post or comment toggles an `isActive` boolean state rather than inserting/deleting records dynamically.
